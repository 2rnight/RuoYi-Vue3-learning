## 第 31 课：标准 CRUD 页面拆解（以用户管理为例）

### 31.1 学习目标

- 能把列表页拆成四部分：**模板（template）**、**状态（state）**、**方法（methods）**、**接口（api）**。
- 熟悉 `getList`、`handleQuery`、`resetQuery`、`handleAdd`、`handleUpdate`、`submitForm`、`handleDelete` 的职责。
- 理解 `ids`、`single`、`multiple` 三个状态如何控制按钮可用性。

### 31.2 课前准备

- 打开 `src/views/system/user/index.vue` 与 `src/api/system/user.js`。
- 在浏览器中打开用户管理页，准备好一个测试用户。

### 31.3 知识讲解

#### （一）四部分拆解

| 部分 | 用户页中的位置 | 作用 |
| --- | --- | --- |
| 模板 | `el-form`（搜索）、工具栏按钮、`el-table`、`pagination`、`el-dialog`（表单） | 展示与交互入口 |
| 状态 | `userList`、`total`、`loading`、`ids`、`single`、`multiple`、`queryParams`、`form`、`open` | 页面的全部数据 |
| 方法 | `getList`、`handleQuery`、`resetQuery`、`handleAdd` 等 | 把用户操作翻译为状态变化与接口调用 |
| 接口 | `src/api/system/user.js` 中的 `listUser`、`addUser`、`updateUser`、`delUser` 等 | 与后端通信，只负责请求 |

> 设计原则：**接口文件不含页面逻辑，页面不直接拼 URL**。这一分层与第 22 课的接口模块化一致。

#### （二）查询链路

```js
const queryParams = ref({ pageNum: 1, pageSize: 10, userName: undefined, ... })
const dateRange = ref([])

function getList() {
  loading.value = true
  listUser(proxy.addDateRange(queryParams.value, dateRange.value)).then(res => {
    loading.value = false
    userList.value = res.rows
    total.value = res.total
  })
}

function handleQuery() {
  queryParams.value.pageNum = 1   // 查询时回到第一页
  getList()
}

function resetQuery() {
  dateRange.value = []
  proxy.resetForm("queryRef")     // 清空搜索表单（第 28 课）
  queryParams.value.deptId = undefined
  proxy.$refs.deptTreeRef.setCurrentKey(null)
  handleQuery()
}
```

- `handleQuery` 与 `getList` 的区别：**查询要回到第一页**，而翻页、刷新只需要调用 `getList`；
- `resetQuery` 先清空条件，再调用 `handleQuery`，保证"重置"后看到的是完整列表的第一页。

#### （三）选择状态：`ids`、`single`、`multiple`

```js
const ids = ref([])
const single = ref(true)
const multiple = ref(true)

function handleSelectionChange(selection) {
  ids.value = selection.map(item => item.userId)
  single.value = selection.length != 1
  multiple.value = !selection.length
}
```

工具栏按钮据此禁用：

```vue
<el-button :disabled="single" @click="handleUpdate">修改</el-button>   <!-- 只能选一条 -->
<el-button :disabled="multiple" @click="handleDelete">删除</el-button> <!-- 至少选一条 -->
```

#### （四）修改、新增与提交

```js
function submitForm() {
  proxy.$refs["userRef"].validate(valid => {
    if (valid) {
      if (form.value.userId != undefined) {
        updateUser(form.value).then(() => { /* 提示、关闭弹窗、getList */ })
      } else {
        addUser(form.value).then(() => { /* 提示、关闭弹窗、getList */ })
      }
    }
  })
}
```

- 用 `form.value.userId` 是否存在区分"新增"与"修改"，同一个弹窗复用；
- 表单校验通过 `proxy.$refs["userRef"].validate` 完成（第 11 课）；
- 成功后先关闭弹窗（`open.value = false`），再刷新列表。

#### （五）删除

```js
function handleDelete(row) {
  const userIds = row.userId || ids.value
  proxy.$modal.confirm('是否确认删除用户编号为"' + userIds + '"的数据项？').then(function () {
    return delUser(userIds)
  }).then(() => {
    getList()
    proxy.$modal.msgSuccess("删除成功")
  }).catch(() => {})
}
```

- `row.userId || ids.value`：行内按钮传入 `row`，工具栏按钮不传参，因此这一行同时支持两种入口；
- 取消确认时 Promise reject，由 `.catch(() => {})` 静默处理（第 30 课）。

#### （六）权限与字典

- 每个按钮都带 `v-hasPermi`，如 `['system:user:add']`，无权限时按钮不渲染（第 18 课）；
- 页面的字典通过 `useDict` 获取：`const { sys_normal_disable, sys_user_sex } = useDict(...)`（第 29 课）；
- 状态列使用 `el-switch`，切换时调用 `handleStatusChange`。

**任务 C：分析 `handleDelete` 的两种入口**

行内删除按钮与工具栏删除按钮分别传入什么参数？`const userIds = row.userId || ids.value` 中哪一个分支会生效？

<details>
<summary>参考答案</summary>

- 行内按钮调用 `handleDelete(scope.row)`，`row.userId` 有值，因此删除的是该行用户；
- 工具栏按钮的模板是 `@click="handleDelete"`（没有写括号），Vue 会把点击事件对象作为第一个参数传入，所以 `row` 是一个 `MouseEvent`，`row.userId` 为 `undefined`，于是回退到 `ids.value`，删除所有勾选的用户；
- 这一写法依赖"事件对象没有 `userId` 属性"这一事实，属于偶然正确。更健壮的写法是模板中写 `@click="handleDelete()"`，函数里用 `row?.userId`，可作为代码审查时的讨论点。

> 注：上述事件参数的行为来自 Vue 的事件处理约定，可在浏览器控制台中打印 `row` 验证。

</details>

## 第 32 课：用户、角色与授权

### 32.1 学习目标

- 理解用户与角色是多对多关系，并能说出中间数据如何提交。
- 理解"按用户分配角色"（`authRole`）与"按角色分配用户"（`authUser`、`selectUser`）两个入口的区别。
- 理解子页面的路由参数（`:userId`、`:roleId`）与 `activeMenu` 的作用。
- 了解角色的菜单权限与数据权限在哪里配置。

### 32.2 课前准备

- 打开 `src/views/system/user/authRole.vue`、`src/views/system/role/authUser.vue`、`src/views/system/role/selectUser.vue`。
- 打开 `src/router/index.js` 中 `/system/user-auth`、`/system/role-auth` 两段路由。

### 32.3 知识讲解

#### （一）多对多关系

- 一个用户可以拥有多个角色；一个角色可以分配给多个用户；
- 数据库中通常使用中间表（如 `sys_user_role`）保存二者的关联；
- 前端不关心中间表，只需要提交"用户 ID + 角色 ID 列表"。

#### （二）入口一：用户页"分配角色"

用户页操作列的按钮调用：

```js
function handleAuthRole(row) {
  const userId = row.userId
  router.push("/system/user-auth/role/" + userId)
}
```

子页面 `authRole.vue` 的关键逻辑：

```js
const route = useRoute()
// 进入页面时：取出 userId，请求该用户已有的角色
getAuthRole(userId).then(response => { /* 回填 roleIds 与角色列表 */ })

// 提交时：把选中的角色 ID 用逗号拼接
const rIds = roleIds.value.join(",")
updateAuthRole({ userId: userId, roleIds: rIds }).then(() => { /* 返回用户页 */ })
```

接口：

| 方法 | 地址 | 用途 |
| --- | --- | --- |
| `getAuthRole(userId)` | `GET /system/user/authRole/{userId}` | 查询用户及其角色 |
| `updateAuthRole({ userId, roleIds })` | `PUT /system/user/authRole` | 保存授权 |

#### （三）入口二：角色页"分配用户"

角色页操作列的按钮调用 `handleAuthUser(row)`，跳转到 `/system/role-auth/user/{roleId}`。子页面 `role/authUser.vue` 分为两块：

1. **已授权用户列表**：`allocatedUserList`（`/system/role/authUser/allocatedList`），每行可"取消授权"（`authUserCancel`，单个）或批量取消（`authUserCancelAll`）；
2. **添加用户**：点击按钮打开 `selectUser.vue`，它通过 `unallocatedUserList`（未授权用户列表）查询用户，勾选后调用 `authUserSelectAll`（`/system/role/authUser/selectAll`）批量授权。

```js
// selectUser.vue 的确认方法（节选）
authUserSelectAll({ roleId: roleId, userIds: uIds }).then(res => {
  // 提示成功，触发父组件的 "ok" 事件刷新列表
  emit("ok")
})
```

`selectUser.vue` 通过 `defineProps` 接收 `roleId`，并通过 `defineEmits(["ok"])` 通知父页面刷新。这是第 8 课的"子组件向父组件发事件"。

#### （四）路由参数驱动的子页面

```js
{
  path: '/system/user-auth',
  component: Layout,
  hidden: true,                    // 不在侧边栏显示
  children: [{
    path: 'role/:userId(\\d+)',    // 只接受数字参数
    component: () => import('@/views/system/user/authRole'),
    meta: { title: '分配角色', activeMenu: '/system/user' }
  }]
}
```

- `hidden: true`：子页面只能通过按钮进入，不出现在菜单中；
- `:userId(\\d+)`：正则限制参数必须是数字，避免非法路径进入页面；
- `activeMenu: '/system/user'`：进入子页面后，侧边栏仍高亮"用户管理"（第 15 课）。

> 同理，`/system/role-auth/user/:roleId`、`/system/dict-data/index/:dictId`、`/monitor/job-log/index/:jobId` 都是这种"隐藏子路由 + 路由参数"的模式。

#### （五）角色的菜单权限与数据权限

角色的新增/修改表单中，除基本信息外还有两个入口：

- **菜单权限**：树形多选（`menuCheckStrictly` 控制"父子联动"），保存时提交选中的菜单 ID，决定该角色能看到哪些菜单与按钮；
- **数据权限**：`dataScope` 下拉选择，选项为：

| 值 | 含义 |
| --- | --- |
| `1` | 全部数据权限 |
| `2` | 自定数据权限（需选择部门，`v-show="form.dataScope == 2"`） |
| `3` | 本部门数据权限 |
| `4` | 本部门及以下数据权限 |
| `5` | 仅本人数据权限 |

> 数据权限的**真正过滤**发生在后端查询时，前端只负责配置。第 39 课会再次讨论前端控制的边界。

## 第 33 课：部门、岗位与菜单管理

### 33.1 学习目标

- 理解部门管理的树形表格结构，以及"新增子级"与"保存排序"的实现。
- 理解菜单的三种类型（目录 `M`、菜单 `C`、按钮 `F`）及其表单字段差异。
- 能对比岗位管理（标准 CRUD）与部门、菜单（树形）的异同。

### 33.2 课前准备

- 打开 `src/views/system/dept/index.vue`、`src/views/system/menu/index.vue`、`src/views/system/post/index.vue`。
- 在部门管理中找到一个有子部门的节点。

### 33.3 知识讲解

#### （一）部门管理：树形表格

- 表格使用 `row-key="deptId"`，支持展开/折叠；页面提供"展开/折叠全部"（`toggleExpandAll`）；
- 操作列中：
  - 修改：`handleUpdate(scope.row)`；
  - 新增：`handleAdd(scope.row)`，把当前行作为父级；
  - 删除：`v-if="scope.row.parentId != 0"`，**根部门不显示删除按钮**。

```js
function handleAdd(row) {
  // 点击某部门的"新增"，预填其 deptId 为父级 parentId
  // 通过 form.parentId 传给后端，形成父子关系
}
```

**保存排序**是部门页的特色：页面先记录原始排序 `originalOrders`，用户在表格中修改 `orderNum` 后，`handleSaveSort` 只提交发生变化的记录：

```js
updateDeptSort({
  deptIds: changedDeptIds.join(","),
  orderNums: changedOrderNums.join(",")
})
```

- 没有变化时提示"未检测到排序修改"，不发请求；
- 接口为 `PUT /system/dept/updateSort`。这是"只提交差异"的优化思路。

#### （二）菜单管理：三种类型

菜单表单中，`menuType` 决定哪些字段出现：

| 类型 | 值 | 典型字段 | 说明 |
| --- | --- | --- | --- |
| 目录 | `M` | 名称、图标、路由地址 | 只作分组，不对应页面（默认值为 `M`） |
| 菜单 | `C` | 名称、路由地址、组件路径、路由名称、权限标识 | 对应一个页面 |
| 按钮 | `F` | 名称、权限标识 | 不显示在侧边栏，用于 `v-hasPermi` |

表单的显隐由以下规则控制：

```vue
<el-col v-if="form.menuType != 'F'"> ... 路由地址、是否外链 ... </el-col>
<el-col v-if="form.menuType == 'C'"> ... 组件路径、路由名称 ... </el-col>
<el-col v-if="form.menuType != 'M'"> ... 权限标识 ... </el-col>
```

- 列表中的标签：`M` 且 `isFrame='0'` 显示为"外链"，`M` 显示为"目录"，`C` 显示为"菜单"，`F` 显示为"按钮"；
- 新增时的父级：`handleAdd(row)` 中 `row.menuId` 存在则作为父级，否则 `parentId = 0`（根级）。

> 权限标识 `perms` 的格式为 `模块:功能:动作`，如 `system:user:add`，与按钮上的 `v-hasPermi` 一一对应（第 18 课）。

#### （三）岗位管理：标准 CRUD

岗位页结构与用户页一致，接口为 `/system/post/list`、`/system/post`（新增/修改）、`/system/post/{postId}`（删除）。它是"不带树、不带弹窗复杂字段"的最简 CRUD，适合作为练习的起点。

#### （四）三者对比

| 维度 | 部门 | 菜单 | 岗位 |
| --- | --- | --- | --- |
| 数据结构 | 树 | 树 | 平铺列表 |
| 表格组件 | 树形表格 | 树形表格 | 普通表格 |
| 特殊操作 | 保存排序、新增子级 | 类型切换、图标选择 | 无 |

### 34.3 知识讲解

#### （一）字典：两级结构

```
字典类型 sys_user_sex（名称"用户性别"，以下为示例数据）
  ├── 字典数据 "男"  value=0   listClass=default
  ├── 字典数据 "女"  value=1   listClass=default
  └── 字典数据 "未知" value=2   listClass=default
```

- **字典类型**（`/system/dict/type/...`）：定义一组字典的"类别"，如 `sys_user_sex`；
- **字典数据**（`/system/dict/data/...`）：该类别下的具体选项，包含 `dictLabel`（显示文字）、`dictValue`（存储值）、`listClass`（标签样式）等。

页面之间的跳转：字典类型列表的操作按钮调用 `proxy.$tab.openPage("字典数据", '/system/dict-data/index/' + row.dictId)`，打开字典数据页（第 19 课的页签操作）。字典数据页通过 `route.params.dictId` 找到对应的字典类型。

#### （二）字典在前端的使用

```js
const { sys_normal_disable, sys_user_sex } = useDict("sys_normal_disable", "sys_user_sex")
```

- `useDict` 请求 `GET /system/dict/data/type/{dictType}` 并缓存（第 29 课）；
- 下拉框中使用 `v-for="dict in sys_user_sex"`，表格中使用 `<dict-tag :options="sys_normal_disable" :value="scope.row.status" />`（第 27 课）。

> 因此，**新增字典数据后，前端需要刷新字典缓存**。字典类型列表提供了"刷新缓存"的接口：`DELETE /system/dict/type/refreshCache`（第 22 课的接口模块化）。

#### （三）参数设置：`configKey`

参数是"键值对"形式的系统配置，例如初始密码 `sys.user.initPassword`。前端通过全局方法读取：

```js
// src/main.js
app.config.globalProperties.getConfigKey = getConfigKey

// 用户页 onMounted 中
proxy.getConfigKey("sys.user.initPassword").then(response => {
  initPassword.value = response.msg
})
```

接口：`GET /system/config/configKey/{configKey}`。注意取值是 `response.msg`，这是 RuoYi 接口返回的一个约定（第 20 课的响应结构）。

参数页的增删改使用标准 CRUD（同第 31 课），接口为 `/system/config/list`、`/system/config`、`/system/config/{configId}`，并提供 `refreshCache` 刷新参数缓存。

#### （四）通知公告

- 列表页的公告类型与状态都使用 `DictTag` 展示，分别对应字典 `sys_notice_type` 与 `sys_notice_status`；
- 内容使用富文本编辑器 `<editor v-model="form.noticeContent" :min-height="192" />`（第 27 课）；
- 操作列的"阅读人员"按钮打开 `ReadUsers.vue`，它调用 `listNoticeReadUsers`（`/system/notice/readUsers/list`）查询已读/未读人员，支持分页与搜索。

接口中还有：
- `GET /system/notice/listTop`：获取顶部通知列表（供首页通知组件使用）；
- `POST /system/notice/markRead`：标记单条已读；
- `POST /system/notice/markReadAll`：全部已读。

#### （五）首页通知组件

`src/layout/components/HeaderNotice/index.vue` 使用 `el-popover` 展示通知列表：

- 列表项按 `item.isRead` 切换样式（`is-read`），未读与已读视觉不同；
- 点击某条通知调用 `previewNotice`，打开 `DetailView.vue` 查看详情；

### 35.3 知识讲解

#### （一）监控页面的共同特点

| 特点 | 对应设计 |
| --- | --- |
| 数据量大 | 必须分页，且常提供"清空"或"清理"操作 |
| 多为只读 | 不提供新增、修改，只提供查询、删除、导出 |
| 有时效性 | 在线用户、服务器状态需要刷新 |
| 带字典筛选 | 操作类型、状态等字段使用 `sys_oper_type`、`sys_common_status` 等字典 |

#### （二）在线用户

- 接口：`GET /monitor/online/list`；
- 操作：强制下线 `handleForceLogout(row)`，调用 `forceLogout(row.tokenId)`（`DELETE /monitor/online/{tokenId}`），需要 `monitor:online:forceLogout` 权限；
- 原理：在线用户的状态基于 Token（第 16 课登录流程），强制下线即让该 Token 失效。

#### （三）登录日志

- 接口：`/monitor/logininfor/list`；
- 操作：删除、清空（`/monitor/logininfor/clean`）、解锁（`/monitor/logininfor/unlock/{userName}`）；
- **解锁**用于账号因多次输错密码而被锁定时解除限制，对应按钮的权限为 `monitor:logininfor:unlock`。

#### （四）操作日志与详情

- 接口：`/monitor/operlog/list`（列表）、`/monitor/operlog/{operId}`（详情）、`/monitor/operlog/clean`（清空）；
- 列表支持按操作类型（字典 `sys_oper_type`）与状态（`sys_common_status`）筛选；
- 点击"详情"打开 `detail.vue` 弹窗（`v-model:visible`），展示请求方法、参数、返回结果、耗时等。

> 操作日志由后端记录（具体实现通常是切面），因此你的增删改操作一般会留下记录（第 39 课会讨论日志与安全）。以你所用后端版本为准。

#### （五）定时任务与执行日志

- 任务列表：`/monitor/job/list`；启停开关调用 `changeJobStatus`（`PUT /monitor/job/changeStatus`）；立即执行调用 `runJob`（`PUT /monitor/job/run`）；
- 执行日志：点击"更多"中的执行日志，`handleJobLog(row)` 跳转 `/monitor/job-log/index/{jobId}`；
- 日志列表中的"详细"按钮打开 `detail.vue`；
- 路由为隐藏子路由（同第 32 课），`jobId` 为 0 时表示查看全部日志（`log.vue` 中 `jobId != 0` 时才按任务过滤）。

#### （六）服务监控、缓存监控

- **服务监控** `monitor/server`：请求 `/monitor/server` 获取服务器信息并展示（图表实现以该目录下组件为准）；
- **缓存监控** `monitor/cache`：`<script setup name="Cache">`，使用 ECharts 绘制命令统计与内存图表；它还调用 `/monitor/cache/getNames`、`getKeys`、`getValue`、`clearCacheName`、`clearCacheKey`、`clearCacheAll` 等接口，支持按缓存名查看与清理。

> `name="Cache"` 是 `<script setup>` 的组件名声明，用于 `keep-alive` 缓存匹配（第 9 课）。

- 页面本身几乎没有逻辑，只把 Swagger UI 的地址交给 `iFrame` 组件；
- `VITE_APP_BASE_API` 来自环境变量（第 3 课），开发环境下指向代理前缀。

#### （二）代理配置

`vite.config.js` 中的代理：

```js
proxy: {
  '/dev-api': {
    target: baseUrl,
    rewrite: (p) => p.replace(/^\/dev-api/, '')   // 去掉前缀再转发
  },
  '^/v3/api-docs/(.*)': {
    target: baseUrl                               // 接口文档数据直接转发
  }
}
```

- `/dev-api` 前缀：前端请求统一加前缀，由 Vite 去掉前缀后转发给后端（第 4 课）；
- `^/v3/api-docs/(.*)`：Swagger UI 页面加载接口定义（OpenAPI JSON）时访问的路径，需要单独代理；
- 这两条规则共同保证"浏览器只访问前端开发服务器，由它转发给后端"，避免跨域（第 4 课）。

> 与第 3 课讲的 `.env` 文件呼应：`VITE_APP_BASE_API` 决定前缀，`baseUrl` 决定真正的后端地址。

#### （三）数据库监控 iframe 嵌入

第 35 课的 `druid` 页面用的也是 `i-frame`，区别在于它的地址是 `/druid/login.html`。两者都说明：**对于已有成熟页面的后端工具，前端可以选择嵌入而不是重写**。

#### （四）`RuoYi/Doc` 与 `RuoYi/Git`

- `components/RuoYi/Doc`：框架的文档入口，链接地址以代码中的配置为准；
- `components/RuoYi/Git`：页面右上角的代码仓库入口，示例中指向 Gitee 仓库地址，并通过 `svg-icon` 显示图标（第 5 课的 SVG 图标）；
- 两者都是**外部链接组件**，属于框架的展示型信息，不影响业务。

#### （五）前端页面与接口文档的对应

以"用户列表"为例：

| 前端 | 接口文档中的对应 |
| --- | --- |
| `listUser(query)` → `GET /system/user/list` | 查找 `system/user` 分组下的 `list` 接口 |
| `queryParams` 的 `pageNum`、`pageSize` | 接口的查询参数 |
| `proxy.addDateRange` 生成的 `params[beginTime]` | 接口参数中的 `params` 对象（日期区间） |
| 返回的 `rows`、`total` | 接口响应结构中的 `TableDataInfo` |

这一对照是"从页面反推接口"的基本方法，也是调试时的常用手段。

<details>
<summary>参考答案</summary>

**步骤**
1. 在 Swagger 页面的分组列表中找到 `岗位管理` 或 `system/post` 相关分组；
2. 展开 `POST /system/post`，查看 Request body 的 Schema，字段通常包括 `postName`、`postCode`、`postSort`、`status`、`remark` 等；
3. 打开 `src/api/system/post.js`，`addPost(data)` 的 `url` 为 `/system/post`，`method` 为 `post`，`data` 直接传入表单对象。

**对比要点**
- 一致：页面表单字段（如 `postName`、`postCode`）与接口请求体字段名应一致，否则后端无法绑定；
- 不一致的常见情况：
  - 页面有但接口没有的字段（如仅用于前端展示的 `dictLabel`），提交时通常会被忽略或导致报错，视后端校验而定；
  - 接口必填而页面没有的字段，会导致后端返回校验错误。

> 具体字段以你所用版本的接口文档为准，请以 Swagger 中的 Schema 为最终依据。

**任务 B：分析代理前缀**

如果把前端的请求地址写成 `http://localhost:8080/system/user/list`（绕过代理直接访问后端），会有什么问题？请结合 `vite.config.js` 的配置说明。

<details>
<summary>参考答案</summary>

- 直接访问后端时，浏览器的请求与当前前端页面的源（如 `localhost:80xx`）不同，属于跨域请求，可能被浏览器的 CORS 策略拦截；
- 通过 `/dev-api` 前缀请求时，请求与页面同源，Vite 代理在服务端转发，不受浏览器跨域限制；
- 因此，统一使用 `VITE_APP_BASE_API` 前缀是为了让开发环境与生产环境的请求路径保持一致，并避免跨域问题。

</details>
