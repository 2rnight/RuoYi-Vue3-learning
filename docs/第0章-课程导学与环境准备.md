### 1.3 知识讲解

#### （一）若依是什么

若依（RuoYi）是一套面向企业后台管理的快速开发框架，常用于网站管理后台、会员中心、CMS、CRM、OA 等场景。它采用**前后端分离**架构：

```
┌──────────────────────┐        HTTP / JSON         ┌──────────────────────┐
│  前端（本仓库）        │ ─────────────────────────► │  后端（RuoYi-Vue）     │
│  Vue 3 + Vite         │   /dev-api/xxx（代理）      │  SpringBoot           │
│  运行在浏览器中        │ ◄───────────────────────── │  提供 REST 接口与数据  │
└──────────────────────┘     { code, msg, data }    └──────────────────────┘
```

- **前端**负责页面展示、交互、路由与权限的前端侧控制，以及调用接口。
- **后端**负责业务逻辑、数据库访问、真正的权限校验和数据安全。

> 重要认识：前端的权限控制（隐藏按钮、隐藏菜单）只是体验层面的控制，**安全边界必须由后端保证**。这个观念会贯穿整个课程。

#### （二）版本演进：三个前端版本

根据 README 中的对比表，若依前端目前有三个主要版本：

| 对比项 | RuoYi-Vue2 | RuoYi-Vue3（本仓库） | RuoYi-Vue3-TypeScript |
| --- | --- | --- | --- |
| 前端框架 | Vue 2 | Vue 3 | Vue 3 |
| 脚本语言 | JavaScript | JavaScript | TypeScript |
| 构建工具 | Vue CLI | Vite | Vite |
| UI 组件库 | Element UI | Element Plus | Element Plus |
| 状态管理 | Vuex | Pinia | Pinia |
| 路由管理 | Vue Router 3 | Vue Router 4 | Vue Router 4 |
| 维护状态 | 当前维护重心已转移 | 官方主推的活跃版本 | 适合多人协作的企业项目 |

**学习建议**：本课程以 Vue3-JavaScript 版本为主。学完之后，再对比 TypeScript 版本，会更容易理解"类型"带来的收益与成本。

### 2.3 知识讲解

#### （一）前端依赖安装

在仓库根目录执行：

```bash
# 推荐：使用 yarn（可选国内镜像加速）
yarn --registry=https://registry.npmmirror.com

# 或使用 npm
npm install
```

- 依赖会被安装到 `node_modules/`，该目录已被 `.gitignore` 忽略，**不要提交到 Git**。
- 仓库忽略了 `package-lock.json` 与 `yarn.lock`，因此不同机器安装的依赖版本可能略有差异，以 `package.json` 声明的版本为准。

#### （二）`package.json` 中的常用脚本

| 命令 | 实际执行 | 用途 |
| --- | --- | --- |
| `yarn dev` | `vite` | 启动开发服务器，默认端口 80，并自动打开浏览器 |
| `yarn build:prod` | `vite build` | 生产环境打包，产物输出到 `dist/` |
| `yarn build:stage` | `vite build --mode staging` | 预发/测试环境打包，使用 `.env.staging` |
| `yarn preview` | `vite preview` | 在本地预览打包后的 `dist/` |

> 注意：`yarn build:prod` 使用的是 **`production` 模式**（Vite 默认模式），对应 `.env.production`。

#### （三）后端服务

前端开发服务器会把接口请求转发给后端。打开 `vite.config.js`，可以看到：

```js
const baseUrl = 'http://localhost:8080' // 后端接口
// ...
server: {
  port: 80,
  host: true,
  open: true,
  proxy: {
    '/dev-api': {
      target: baseUrl,
      changeOrigin: true,
      rewrite: (p) => p.replace(/^\/dev-api/, '')
    },
    '^/v3/api-docs/(.*)': {
      target: baseUrl,
      changeOrigin: true,
    }
  }
}
```

因此：

- 后端需要运行在 **`localhost:8080`**。如果你的后端端口不同，需要修改 `baseUrl`。
- 浏览器请求 `http://localhost:80/dev-api/login`，开发服务器会把它代理为 `http://localhost:8080/login`（去掉了 `/dev-api` 前缀）。
- 这种做法的好处：浏览器看到的是同源请求，**避免跨域（CORS）问题**。

#### （四）环境变量与接口前缀

不同环境使用不同的接口前缀，它们都定义在 `.env.*` 文件中：

| 文件 | `VITE_APP_ENV` | `VITE_APP_BASE_API` | 适用场景 |
| --- | --- | --- | --- |
| `.env.development` | `development` | `/dev-api` | 本地开发（`yarn dev`） |
| `.env.staging` | `staging` | `/stage-api` | 测试/预发布构建（`yarn build:stage`） |
| `.env.production` | `production` | `/prod-api` | 正式构建（`yarn build:prod`） |

> 注意：开发环境的 `/dev-api` 由 Vite 代理转发；测试与生产环境的 `/stage-api`、`/prod-api` 需要由你的 Web 服务器（如 Nginx）配置反向代理，Vite 的代理配置对它们**不生效**。这是部署时的常见问题，第 6 课会详细讲解。

#### （五）登录流程概览（先建立印象，后面章节再深入）

```
浏览器输入账号密码
   │
   ▼
GET  /dev-api/captchaImage        获取验证码（图片 + uuid）
   │
   ▼
POST /dev-api/login               提交 username、password、code、uuid
   │                              返回 { code: 200, token: "..." }
   ▼
保存 token → 请求 GET /dev-api/getInfo 获取用户信息与权限
   │
   ▼
GET  /dev-api/getRouters           获取菜单，生成动态路由
   │
   ▼
进入首页
```

这些接口的定义位于 `src/api/login.js` 与 `src/api/menu.js`。

### 2.4 操作步骤

#### 步骤 1：启动后端

1. 按后端仓库 README 完成数据库初始化与配置（数据库连接、Redis 地址等）。
2. 启动后端应用，确认控制台没有报错，并且服务监听在 `8080` 端口。
3. 在浏览器或终端中验证后端可访问（具体接口以后端为准，例如能访问其接口文档页面）。

#### 步骤 2：安装前端依赖并启动

```bash
cd RuoYi-Vue3-learning
yarn --registry=https://registry.npmmirror.com
yarn dev
```

启动成功后，终端会输出类似以下内容（端口与地址以实际输出为准）：

```
VITE v6.x.x  ready in xxx ms
➜  Local:   http://localhost/
➜  Network: http://192.168.x.x/
```

> 如果本机 80 端口被占用，Vite 会报错。可以先停止占用 80 端口的程序（如 Nginx、IIS、其它 Web 服务），或修改 `vite.config.js` 中的 `port`。Windows 下也可以直接双击 `bin/run-web.bat` 启动。

#### 步骤 3：登录系统

1. 访问 `http://localhost` 或终端中显示的地址。
2. 在登录页输入：账号 `admin`，密码 `admin123`。
3. 如果页面显示验证码，请输入图片中的字符。
4. 登录成功后进入首页，侧边栏应能看到各功能菜单。

#### 步骤 4：用开发者工具观察登录请求

1. 按 `F12` 打开开发者工具，切换到 **Network（网络）** 面板。
2. 勾选 **Preserve log（保留日志）**，然后重新登录。
3. 依次找到以下请求并记录信息：

| 请求 | 方法 | 你需要记录的信息 |
| --- | --- | --- |
| `captchaImage` | GET | 请求 URL 的完整路径，响应中的 `uuid` 与 `img` 字段（图片的 base64 数据）。 |
| `login` | POST | Request URL、Request Headers 中的 `Content-Type`，Request Payload 中的字段名。 |
| `getInfo` | GET | 请求头中是否带有 `Authorization: Bearer ...`。 |
| `getRouters` | GET | 响应中菜单数据的大致结构（是否有 `path`、`component`、`children`）。 |

**思考**：`login` 请求的 Payload 中，`password` 字段的值是明文吗？如果不是，它可能经过了什么处理？（提示：可以对照 `src/utils/jsencrypt.js` 与 `src/views/login.vue`，留到第 29 课深入。）

#### 步骤 5：查看本地存储的 Token

1. 在开发者工具中切换到 **Application（应用）** 面板（Chrome）或 **Storage（存储）**（Firefox）。
2. 在左侧找到 **Cookies** 或 **Local Storage** 下的当前站点。
3. 找到与 token 相关的记录，并观察它的存放位置。

> 相关代码位于 `src/utils/auth.js`，你可以打开查看它使用的存储方式。这是第 5 课与第 39 课的讨论重点。

### 2.5 常见问题排查

| 现象 | 可能原因 | 排查方法 |
| --- | --- | --- |
| `yarn` 安装依赖很慢或失败 | 网络或镜像问题 | 确认 `--registry` 参数；或换用 npm 并检查网络 |
| 启动报 `EADDRINUSE` / 端口被占用 | 80 端口已被占用 | 关闭占用程序，或修改 `vite.config.js` 的 `port` |
| 登录提示"后端接口连接异常" | 后端未启动，或端口不是 8080 | 访问后端地址确认；检查 `baseUrl` |
| 登录提示验证码错误 | 验证码过期或输入有误 | 点击验证码图片刷新后重新输入 |
| 登录后页面空白或菜单为空 | `getRouters` 失败或权限数据异常 | 在 Network 面板查看 `getRouters` 的响应与状态码 |
| 登录后被反复跳回登录页 | Token 未正确保存，或后端 `getInfo` 报错 | 检查 `Authorization` 请求头与 `getInfo` 响应 |
| 请求返回 401 | 登录已过期 | 重新登录 |
| 修改了 `.env` 没有生效 | Vite 只在启动时读取环境变量 | 停止并重新执行 `yarn dev` |
| 页面中文乱码 | 文件编码或服务器编码问题 | 确认文件为 UTF-8；Windows 下注意 `bin/*.bat` 的编码 |

### 2.7 课堂自测

1. `yarn dev` 与 `yarn build:prod` 的区别是什么？它们分别使用哪个环境变量文件？
2. 为什么开发环境要通过 `/dev-api` 前缀访问后端，而不是直接访问 `http://localhost:8080`？
3. 生产环境的 `/prod-api` 为什么不能只靠 Vite 的代理解决？
4. 登录时 `captchaImage` 接口返回的 `uuid` 在 `login` 请求中起什么作用？
5. 为什么不应该把 `node_modules/` 和 `dist/` 提交到 Git？

<details>
<summary>参考答案（先自己思考再查看）</summary>

1. `yarn dev` 启动开发服务器，用于本地开发，使用 `.env.development`；`yarn build:prod` 生成生产包，使用 `.env.production`（`production` 模式）。
2. 通过同源的 `/dev-api` 访问，开发服务器代理转发到后端，浏览器不会因跨域被拦截，也不需要后端额外配置 CORS；同时便于统一管理前缀。
3. Vite 代理只存在于开发服务器中。生产环境下，前端是静态文件，需要由 Nginx 等 Web 服务器配置反向代理，把 `/prod-api` 转发到后端。
4. `uuid` 是验证码的标识，后端通过它找到对应的验证码答案进行校验。前端需要把用户输入的验证码和 `uuid` 一起提交。
5. 两者都是可以通过 `package.json` 与锁文件重新生成的产物或依赖，体积大且与平台相关，提交会造成仓库膨胀、冲突频繁。

</details>
