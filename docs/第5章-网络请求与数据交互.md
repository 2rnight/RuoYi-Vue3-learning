### 20.3 知识讲解

#### （一）为什么要封装 Axios

直接在页面中写 `axios.get(...)` 会有以下问题：

- 每个页面都要重复写基础地址、超时时间、Token 注入、错误处理；
- 一旦需要修改全局行为（如统一加请求头），要改很多地方；
- 错误提示风格不统一。

因此项目把这些共性逻辑集中到 `src/utils/request.js`，业务代码只需调用封装好的 `request`。

#### （二）创建实例

```js
import axios from 'axios'

axios.defaults.headers['Content-Type'] = 'application/json;charset=utf-8'

const service = axios.create({
  baseURL: import.meta.env.VITE_APP_BASE_API,   // 如 '/dev-api'
  timeout: 10000                                 // 10 秒超时
})

export default service
```

| 配置 | 含义 | 本项目取值 |
| --- | --- | --- |
| `baseURL` | 所有请求的公共前缀 | 来自环境变量，开发为 `/dev-api` |
| `timeout` | 超过该毫秒数视为超时 | 10000（10 秒） |
| `headers` | 默认请求头 | `Content-Type: application/json;charset=utf-8` |

**`axios.create` 与全局 `axios` 的区别**：`create` 返回一个独立实例，它拥有自己的配置与拦截器，不会污染全局 Axios。`src/utils/request.js` 导出的是这个实例，所以所有业务请求都经过同一套拦截器。

> 注意：第 1 行 `axios.defaults.headers['Content-Type'] = ...` 修改的是**全局默认值**，它会影响项目中直接使用 `axios` 的地方（例如 `download.js`）。这是一个值得留意的细节。

#### （三）单个请求的覆盖配置

同一个实例可以在单个请求中覆盖配置。登录接口与验证码接口就是例子：

```js
// src/api/login.js
export function getCodeImg() {
  return request({
    url: '/captchaImage',
    headers: { isToken: false },     // 自定义请求头：不携带 Token
    method: 'get',
    timeout: 20000                   // 覆盖全局超时：验证码生成可能较慢
  })
}
```

- `timeout: 20000` 覆盖了实例默认的 10 秒；
- `headers` 中的自定义字段（如 `isToken`、`repeatSubmit`）不会被发送到后端，而是由拦截器读取后决定行为（第 21 课讲解）。

#### （四）一个最小接口函数

以用户列表为例（`src/api/system/user.js`）：

```js
import request from '@/utils/request'

export function listUser(query) {
  return request({
    url: '/system/user/list',
    method: 'get',
    params: query           // GET 的查询参数
  })
}
```

调用方式：

```js
listUser({ pageNum: 1, pageSize: 10, userName: 'admin' })
  .then(res => { /* res 为后端返回的 JSON 中的 data 之外的整体 */ })
```

> **重要**：这里的 `.then(res => ...)` 拿到的是响应拦截器 `Promise.resolve(res.data)` 之后的结果，也就是后端返回的整个 JSON（包含 `code`、`msg`、`rows`、`total` 等），而不是 Axios 原始的 `response` 对象。第 21 课会详细说明。

#### （五）请求的完整链路（概览）

```
页面调用 listUser(query)
   │
   ▼
request({ url, method, params }) ── 请求拦截器 ──► Authorization / 参数序列化 / 防重复
   │
   ▼
baseURL + url  →  /dev-api/system/user/list?pageNum=1&...
   │
   ▼  Vite 代理（开发）或 Nginx（生产）
后端 /system/user/list
   │
   ▼  返回 { code, msg, rows, total }
响应拦截器 ── 统一错误码处理 ──► Promise.resolve(res.data)
   │
   ▼
页面 .then(res => ...)
```

### 21.3 知识讲解

#### （一）请求拦截器的整体结构

```js
service.interceptors.request.use(config => {
  const isToken = (config.headers || {}).isToken === false          // ① 是否跳过 Token
  const isRepeatSubmit = (config.headers || {}).repeatSubmit === false  // ② 是否跳过防重复
  const interval = (config.headers || {}).interval || 1000           // ② 防重复的时间间隔

  if (getToken() && !isToken) {                                      // ① 注入 Token
    config.headers['Authorization'] = 'Bearer ' + getToken()
  }

  if (config.method === 'get' && config.params) {                    // ③ GET 参数序列化
    let url = config.url + '?' + tansParams(config.params)
    url = url.slice(0, -1)
    config.params = {}
    config.url = url
  }

  if (!isRepeatSubmit && (config.method === 'post' || config.method === 'put')) {  // ④ 防重复提交
    // ... 见下文
  }
  return config
}, error => {
  console.log(error)
  Promise.reject(error)
})
```

#### （二）职责一：Token 注入与 `isToken`

- 默认情况下，只要本地存在 Token（Cookie `Admin-Token`），就会在请求头中加入 `Authorization: Bearer <token>`。
- 若请求头中设置了 `isToken: false`，则**不注入** Token。典型场景是登录、注册、获取验证码，这些接口在用户未登录时调用。

```js
// src/api/login.js
export function login(username, password, code, uuid) {
  return request({
    url: '/login',
    headers: { isToken: false, repeatSubmit: false },   // 登录不带 Token，且不做防重复
    method: 'post',
    data: { username, password, code, uuid }
  })
}
```

> 注意：`Bearer ` 后面有一个空格，这是 HTTP 认证头的标准格式。后端需要按此格式解析。

#### （三）职责二：GET 参数序列化

Axios 默认会把 `params` 对象转为 URL 查询串，但项目用 `tansParams` 做了自定义序列化，原因是它能正确处理**嵌套对象**（如 `params[beginTime]` 这样的日期区间参数）。

`tansParams` 的核心逻辑（`src/utils/ruoyi.js`）：

- 跳过值为 `null`、`''`、`undefined` 的字段；
- 对象类型的值会展开为 `propName[key]=value` 的形式；
- 结果以 `&` 连接，最后由拦截器去掉末尾的 `&`。

例如 `{ pageNum: 1, params: { beginTime: '2024-01-01' } }` 会被序列化为：

```
?pageNum=1&params%5BbeginTime%5D=2024-01-01
```

#### （四）职责三：防重复提交

这是拦截器中最复杂的部分。它的目标是：**同一个 POST/PUT 请求在很短时间内重复发出，直接拒绝第二次**。

核心逻辑（节选）：

```js
const requestObj = {
  url: config.url,
  data: typeof config.data === 'object' ? JSON.stringify(config.data) : config.data,
  time: new Date().getTime()
}
// 请求数据超过 5MB 时，无法做比对，直接放行并打印警告
const requestSize = Object.keys(JSON.stringify(requestObj)).length
if (requestSize >= 5 * 1024 * 1024) {
  console.warn(`[${config.url}]: 请求数据大小超出允许的5M限制，无法进行防重复提交验证。`)
  return config
}

const sessionObj = cache.session.getJSON('sessionObj')   // 上一次请求记录（sessionStorage）
if (sessionObj === undefined || sessionObj === null || sessionObj === '') {
  cache.session.setJSON('sessionObj', requestObj)        // 第一次：记录
} else {
  const s_url = sessionObj.url
  const s_data = sessionObj.data
  const s_time = sessionObj.time
  if (s_data === requestObj.data && requestObj.time - s_time < interval && s_url === requestObj.url) {
    // 同一地址、同一数据、间隔小于 interval：重复提交
    return Promise.reject(new Error('数据正在处理，请勿重复提交'))
  } else {
    cache.session.setJSON('sessionObj', requestObj)      // 不重复：更新记录
  }
}
return config
```

判断"重复"需要同时满足三个条件：

| 条件 | 含义 |
| --- | --- |
| `url` 相同 | 访问的是同一个接口 |
| `data` 相同 | 提交的内容完全一致 |
| 间隔 `< interval` | 在默认 1000 毫秒内 |

**设计要点**：

- 记录保存在 **sessionStorage**，只对当前标签页有效；
- 只保存**最近一次**请求，不是完整历史；
- 对于数据超过 5MB 的请求，放弃检查，避免序列化成本过高；
- 通过 `repeatSubmit: false` 可以对特定接口关闭检查（如登录）。

> **局限**：这是一种"前端节流"，它无法防止用户在 1 秒后再次提交，也不能代替后端的幂等设计。真正的防重复应由后端保证（如数据库唯一约束、幂等 token）。

#### （五）响应拦截器：统一错误码

```js
service.interceptors.response.use(res => {
  const code = res.data.code || 200                       // 未设置 code 视为成功
  const msg = errorCode[code] || res.data.msg || errorCode['default']

  // 二进制数据（文件下载）直接返回，不做错误码判断
  if (res.request.responseType === 'blob' || res.request.responseType === 'arraybuffer') {
    return res.data
  }

  if (code === 401) { /* 登录过期，弹窗让用户选择重新登录 */ return Promise.reject(...) }
  else if (code === 500) { ElMessage.error(msg); return Promise.reject(new Error(msg)) }
  else if (code === 601) { ElMessage.warning(msg); return Promise.reject(new Error(msg)) }
  else if (code !== 200) { ElNotification.error({ title: msg }); return Promise.reject('error') }
  else { return Promise.resolve(res.data) }             // 成功：返回后端 JSON
}, error => { /* 网络层错误，见下文 */ })
```

按 `code` 的分类处理：

| code | 处理方式 | 典型含义 |
| --- | --- | --- |
| 200 | `Promise.resolve(res.data)`，正常返回 | 成功 |
| 401 | 弹出确认框，用户选择"重新登录"后清理状态并跳转 | 会话过期 |
| 500 | `ElMessage.error` 错误提示，并 reject | 服务端异常 |
| 601 | `ElMessage.warning` 警告提示，并 reject | 业务警告（如"不允许删除"） |
| 其它 | `ElNotification.error` 通知提示，并 reject | 其它业务错误 |

**401 的特殊之处**：

```js
if (!isRelogin.show) {                 // 防止多个请求同时失效而弹出多个对话框
  isRelogin.show = true
  ElMessageBox.confirm('登录状态已过期，您可以继续留在该页面，或者重新登录', ...)
    .then(() => { isRelogin.show = false; useUserStore().logOut().then(() => { location.href = '/index' }) })
    .catch(() => { isRelogin.show = false })
}
```

- `isRelogin.show` 作为"互斥锁"，保证同一时刻只弹出一个确认框；
- 用户可以选择"留在页面"（取消），也可以"重新登录"（退出并刷新）。

#### （六）网络层错误处理

第二个参数（错误回调）处理的是**没有收到有效响应**的情况：

```js
error => {
  let { message } = error
  if (message == "Network Error")            message = "后端接口连接异常"
  else if (message.includes("timeout"))      message = "系统接口请求超时"
  else if (message.includes("Request failed with status code")) message = "系统接口" + message.slice(-3) + "异常"
  ElMessage({ message, type: 'error', duration: 5 * 1000 })
  return Promise.reject(error)
}
```

| Axios 错误信息 | 提示文字 | 常见原因 |
| --- | --- | --- |
| `Network Error` | 后端接口连接异常 | 后端未启动、代理错误、断网 |
| 包含 `timeout` | 系统接口请求超时 | 后端响应慢，或超时时间过短 |
| `Request failed with status code 404` | 系统接口404异常 | 接口路径错误、代理前缀问题 |

> 注意：HTTP 状态码 401 时，Axios 会进入错误回调（而不是成功回调），此时后端如果返回了 `code: 401` 的 JSON，并不会走上面的 401 弹窗逻辑。这是阅读时值得注意的边界。

#### （七）`request.js` 的 `download` 方法

`request.js` 还导出了一个 `download` 方法，它使用 `responseType: 'blob'` 以二进制方式接收文件，并通过 `blobValidate` 区分"文件"和"JSON 错误信息"。详见第 23 课。

<details>
<summary>参考答案（先自己思考再查看）</summary>

1. 不注入 Token。用于登录、注册、验证码等用户尚未登录时调用的接口。
2. 相同的 url、相同的 data，且两次请求时间间隔小于 `interval`（默认 1000 毫秒）。
3. sessionStorage 只在当前标签页内有效，关闭标签页即清空，符合"短时间重复"的判断范围；localStorage 长期保存，不适合存放这类临时记录。
4. 500 使用 `ElMessage.error` 显示错误并 reject；601 使用 `ElMessage.warning` 显示警告并 reject。两者都不会进入成功分支，只是提示的严重程度不同。
5. 前端的判断只针对同一浏览器、较短时间内的重复点击，无法覆盖多人、多端、间隔较长的重复提交。后端需要用唯一约束或幂等设计保证数据正确。

</details>

## 第 22 课：接口模块化与错误码

### 22.1 学习目标

- 掌握路径参数、查询参数与请求体的不同写法。

- 能为一个新模块整理完整的接口清单。

### 22.2 课前准备

- 打开 `src/api/system/dict/data.js`、`src/api/system/dict/type.js`，观察它们的结构。

### 22.3 知识讲解

#### （一）目录结构

```
src/api/
├── login.js          # 登录、注册、退出、获取用户信息、验证码（认证相关）
├── menu.js           # 获取路由 getRouters
├── monitor/          # 监控模块：cache、job、jobLog、logininfor、online、operlog、server
├── system/           # 系统管理：config、dept、menu、notice、post、role、user
│   └── dict/         # 字典子模块：data.js、type.js
└── tool/
    └── gen.js        # 代码生成
```

组织规则：

- **按业务模块分目录**，与 `src/views` 的目录结构大体对应（例如 `api/system/user.js` 对应 `views/system/user/`）；
- 一个文件通常对应一个实体的全部接口（增删改查、导出、状态修改等）；
- 较深的子模块（如字典）再单独建子目录，避免单个文件过大。

#### （二）标准 CRUD 接口的写法

以用户管理为例（`src/api/system/user.js`，节选）：

```js
import request from '@/utils/request'
import { parseStrEmpty } from '@/utils/ruoyi'

// 查询用户列表（GET + 查询参数）
export function listUser(query) {
  return request({ url: '/system/user/list', method: 'get', params: query })
}

// 查询用户详情（GET + 路径参数）
export function getUser(userId) {
  return request({ url: '/system/user/' + parseStrEmpty(userId), method: 'get' })
}

// 新增用户（POST + 请求体）
export function addUser(data) {
  return request({ url: '/system/user', method: 'post', data: data })
}

// 修改用户（PUT + 请求体）
export function updateUser(data) {
  return request({ url: '/system/user', method: 'put', data: data })
}

// 删除用户（DELETE + 路径参数）
export function delUser(userId) {
  return request({ url: '/system/user/' + userId, method: 'delete' })
}
```

这套写法体现了 RESTful 的基本约定：

| 操作 | HTTP 方法 | URL | 参数位置 |
| --- | --- | --- | --- |
| 列表 | GET | `/system/user/list` | 查询参数 `params` |
| 详情 | GET | `/system/user/{id}` | 路径参数 |
| 新增 | POST | `/system/user` | 请求体 `data` |
| 修改 | PUT | `/system/user` | 请求体 `data` |
| 删除 | DELETE | `/system/user/{ids}` | 路径参数 |

#### （三）三种参数的区别

| 参数位置 | 写法 | 适用场景 | 注意事项 |
| --- | --- | --- | --- |
| 查询参数 | `params: query` | 列表筛选、分页 | GET 请求，会经过 `tansParams` 序列化（第 21 课） |
| 路径参数 | `'/user/' + id` | 指定具体资源 | 注意值为空时的 URL 形态 |
| 请求体 | `data: data` | 新增、修改、提交表单 | POST/PUT，数据以 JSON 发送 |

#### （四）`parseStrEmpty`：处理路径参数

```js
export function getUser(userId) {
  return request({ url: '/system/user/' + parseStrEmpty(userId), ... })
}
```

`parseStrEmpty` 的作用是：当参数为 `undefined`、`null` 或空字符串时，返回一个安全的占位值（而不是拼出 `/system/user/undefined`）。这样即使调用方忘记传参，URL 也不会变成无效的字符串。

> 阅读建议：在 `src/utils/ruoyi.js` 中找到 `parseStrEmpty` 的实现，对照它的行为做一次实验。

#### （五）同一模块的分层：`dict/data.js` 与 `dict/type.js`

字典功能分为两层：

- **字典类型**（`type.js`）：如 `sys_user_sex`，相当于分类；
- **字典数据**（`data.js`）：如"男""女"，属于某个类型。

`data.js` 中有一个关键接口：

```js
export function getDicts(dictType) {
  return request({ url: '/system/dict/data/type/' + dictType, method: 'get' })
}
```

它就是 `utils/dict.js` 中 `useDict` 调用的接口（第 13 课）。注意它的路径中用了 **路径参数**（`/type/` + 字典类型），而不是查询参数。

#### （六）接口与页面的解耦

页面组件只关心"要什么数据"，不关心"URL 是什么"：

```js
// 页面中
listUser(queryParams).then(res => { userList.value = res.rows; total.value = res.total })
```

好处：

1. URL 变化时只需改 `api` 文件，页面无需修改；
2. 接口函数可以统一加入日志、缓存、参数转换；
3. 便于单元测试与 Mock（用假数据替换 api 函数）。

#### （七）错误码约定（与第 21 课呼应）

后端返回的标准结构是：

```json
{ "code": 200, "msg": "操作成功", "data": ... }
```

列表接口通常还带有 `rows` 与 `total`。约定如下：

| code | 含义 | 前端处理位置 |
| --- | --- | --- |
| 200 | 成功 | 响应拦截器返回数据 |
| 401 | 未认证/会话过期 | 响应拦截器弹窗 |
| 403 | 无权限（HTTP 状态码或 code） | `errorCode.js` 映射为"当前操作没有权限" |
| 404 | 资源不存在 | `errorCode.js` 映射为"访问资源不存在" |
| 500 | 服务端异常 | 响应拦截器错误提示 |
| 601 | 业务警告 | 响应拦截器警告提示 |
| 其它 | 自定义业务错误 | 响应拦截器通知 |

`src/utils/errorCode.js` 中定义了 401、403、404 与 default 的文字映射：

```js
export default {
  '401': '认证失败，无法访问系统资源',
  '403': '当前操作没有权限',
  '404': '访问资源不存在',
  'default': '系统未知错误，请反馈给管理员'
}
```

响应拦截器中 `const msg = errorCode[code] || res.data.msg || errorCode['default']`，优先级是：**错误码映射 > 后端返回的 msg > 默认文字**。

### 23.1 学习目标

- 掌握项目中 `FileUpload`、`ImageUpload`、`ExcelImportDialog` 三类上传组件的用法。
- 能为导出功能增加合理的错误处理。

### 23.2 课前准备

- 阅读 `src/plugins/download.js`、`src/utils/request.js` 中的 `download` 方法、`src/utils/ruoyi.js` 中的 `blobValidate`。
- 打开 `src/views/system/user/index.vue`，找到"导入""导出"按钮。

### 23.3 知识讲解

#### （一）文件下载的核心问题

普通的 JSON 接口返回文本，而文件下载需要返回**二进制流**。因此前端要解决两件事：

1. 以 `blob` 方式接收响应（`responseType: 'blob'`）；
2. 把 blob 保存为文件（`file-saver` 的 `saveAs`）。

但还有第三个问题：如果后端出错，返回的是 **JSON 错误信息**，而不是文件。前端不能把它也当作文件保存。这正是 `blobValidate` 要解决的。

#### （二）`blobValidate`：区分文件与错误

```js
export function blobValidate(data) {
  return data.type !== 'application/json'
}
```

判断逻辑：后端正常返回文件时，`Content-Type` 为文件类型（如 `application/vnd.ms-excel`），blob 的 `type` 不是 `application/json`，判定为文件；若后端返回了 JSON 错误，blob 的 `type` 为 `application/json`，判定为错误。

#### （三）两套下载实现

**1. `request.js` 中的 `download(url, params, filename, config)`**

这是**业务导出**最常用的方法（页面中 `proxy.download("system/user/export", {...})` 即调用它）。流程：

```js
export function download(url, params, filename, config) {
  downloadLoadingInstance = ElLoading.service({ text: "正在下载数据，请稍候" ... })   // ① 加载遮罩
  return service.post(url, params, {                                                  // ② 通过封装好的 service 发送 POST
    transformRequest: [(params) => tansParams(params)],                              // ③ 表单格式序列化
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' },
    responseType: 'blob',
    ...config
  }).then(async (data) => {
    if (blobValidate(data)) {                                                        // ④ 判断是否为文件
      saveAs(new Blob([data]), filename)                                             //    是：保存
    } else {
      const rspObj = JSON.parse(await data.text())                                   //    否：解析 JSON 错误
      ElMessage.error(errorCode[rspObj.code] || rspObj.msg || errorCode['default'])
    }
    downloadLoadingInstance.close()                                                  // ⑤ 关闭遮罩
  }).catch(() => {
    ElMessage.error('下载文件出现错误，请联系管理员！')
    downloadLoadingInstance.close()
  })
}
```

要点：

- 导出接口使用 **POST + 表单格式**（`x-www-form-urlencoded`），这是为了与后端导出接口的参数绑定方式一致；
- 因为走的是 `service`，所以**会经过拦截器**，Token 与防重复逻辑都生效；
- 响应拦截器中对 `blob` 类型直接 `return res.data`，跳过了 JSON 错误码判断，因此错误判断由这里的 `blobValidate` 完成。

**2. `plugins/download.js`（`$download` 工具）**

这是**文件资源**的下载工具，提供 `name`、`resource`、`zip`、`saveAs`、`printErrMsg` 等方法，例如：

```js
// 通过文件名下载（后端 /common/download）
proxy.$download.name(fileName)
```

与 `request.js` 中的 `download` 相比，它的特点是：

- 使用**裸 `axios`**，而不是封装过的 `service`，因此**不经过项目的拦截器**；
- 需要在代码中手动添加 `Authorization` 请求头；
- 从响应头 `download-filename` 中读取文件名（需要后端暴露该响应头）。

> **对比小结**：`request.js` 的 `download` 用于"页面导出，走 POST，经过拦截器"；`plugins/download.js` 用于"已存在的文件资源，走 GET，绕过拦截器"。阅读时要注意两者在拦截器与 Token 处理上的不同。

#### （四）导出的完整调用示例

以用户导出为例（`src/views/system/user/index.vue`，节选）：

```js
function handleExport() {
  proxy.download("system/user/export", {
    ...queryParams.value
  }, `user_${new Date().getTime()}.xlsx`)
}
```

- 第一个参数是**接口路径**（注意：不带 `/dev-api` 前缀，因为 `service` 会自动加上 `baseURL`）；
- 第二个参数是**查询条件**，与列表页的筛选条件一致，保证导出的数据与列表一致；
- 第三个参数是**文件名**，加上时间戳避免重复。

> 注意：`handleExport` 的参数中使用了 `...queryParams.value`，而 `queryParams` 中的分页字段（`pageNum`、`pageSize`）会一并发送。后端导出接口通常会忽略它们，但这是值得留意的细节。

#### （五）上传组件概览

| 组件 | 用途 | 关键 props | 使用场景 |
| --- | --- | --- | --- |
| `FileUpload` | 通用文件上传 | `action`、`limit`、`fileSize`、`fileType`、`modelValue` | 附件 |
| `ImageUpload` | 图片上传（带预览） | 类似 `FileUpload` | 头像、配图 |
| `ExcelImportDialog` | Excel 导入（弹窗） | `action`、`templateAction`、`templateFileName`、`title` | 用户导入、字典导入 |

**`FileUpload` 的关键实现**：

```js
const uploadFileUrl = ref(import.meta.env.VITE_APP_BASE_API + props.action)  // 拼接完整上传地址
const headers = ref({ Authorization: "Bearer " + getToken() })              // 上传请求头携带 Token
```

- `:action` 绑定上传地址；`:headers` 绑定请求头，因为 `el-upload` 不经过 `request.js`，需要手动传 Token；

**`ExcelImportDialog` 的关键实现**：

```vue
<el-upload :limit="1" accept=".xlsx, .xls" :headers="headers" :action="uploadUrl"

```

- `:auto-upload="false"`：选择文件后不自动上传，用户需要点击确认按钮，给用户留出"修改文件"的机会；

- `uploadUrl` 拼接了 `updateSupport` 参数，表示是否允许覆盖已存在的数据；
- `templateAction` 存在时，弹窗提供"下载模板"按钮，调用 `proxy.download(props.templateAction, ...)`。

以用户导入为例：

```vue
<excel-import-dialog ref="importUserRef" title="用户导入"
  action="/system/user/importData"
  template-action="/system/user/importTemplate"
  ... />
```

#### （六）上传与下载的错误处理

| 场景 | 处理位置 | 说明 |
| --- | --- | --- |
| 导出失败（后端返回 JSON） | `request.js` 的 `download` | `blobValidate` 判断后用 `ElMessage` 提示 |
| 导出网络错误 | `request.js` 的 `download` 的 `catch` | 统一提示"下载文件出现错误" |
| 上传超出大小 | `FileUpload` 的 `beforeUpload` | 前端直接拦截，不发请求 |
| 导入失败 | `ExcelImportDialog` 的 `handleSuccess` | 后端返回的错误信息展示在弹窗中 |

<details>
<summary>参考答案（先自己思考再查看）</summary>

1. 检查 blob 的 `type`：不是 `application/json` 则视为文件；是 `application/json` 则说明后端返回的是错误信息，需要解析并提示。

3. 后端导出接口通常按表单参数绑定查询条件，使用 `x-www-form-urlencoded` 格式与之匹配；`tansParams` 能正确序列化嵌套对象。
4. `el-upload` 直接发起请求，不经过 `request.js`，因此拦截器不会自动注入 Token，需要通过 `:headers` 显式传入。
5. 让用户先选择文件并查看，再点击确认导入，避免误操作直接导入错误的数据。

</details>

## 本章小结

| 课时 | 核心问题 | 关键结论 |
| --- | --- | --- |
| 第 20 课 | 请求如何发出？ | 通过 `axios.create` 得到统一实例，`baseURL` 来自环境变量，超时可按请求覆盖 |
| 第 21 课 | 请求与响应如何被统一处理？ | 请求侧注入 Token、序列化 GET 参数、防重复；响应侧按 `code` 分类处理、网络错误友好提示 |
| 第 22 课 | 接口如何组织？ | 按业务模块分目录；CRUD 对应 HTTP 方法；参数位置各有场景；错误信息按映射优先级展示 |
| 第 23 课 | 文件如何上传下载？ | 下载依赖 `blob` 与 `blobValidate`；页面导出走 `request.js`，文件资源走 `$download`；上传需手动带 Token |

**本章的一个核心观念**：所有网络交互都应经过同一条"管道"——**统一的实例、统一的拦截、统一的错误出口**。页面只需关心业务数据，框架负责身份、安全与异常。理解这条管道，就能快速定位大多数接口问题。
