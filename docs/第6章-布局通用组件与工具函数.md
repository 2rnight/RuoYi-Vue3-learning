### 24.3 知识讲解

#### （一）布局的结构

`src/layout/index.vue` 的模板可以简化为：

```
app-wrapper
├── drawer-bg            （移动端：侧边栏展开时的遮罩）
├── sidebar              （侧边栏，v-if="!sidebar.hide"）
└── main-container
    ├── fixed-header
    │   ├── navbar       （顶部导航栏）
    │   └── tags-view    （标签栏，受 tagsView 设置控制）
    ├── app-main         （主内容区，内含 router-view 与 keep-alive）
    └── settings         （设置面板，抽屉形式）
```

`layout/components/index.js` 统一导出了 `AppMain`、`Navbar`、`Settings`、`TagsView`，`index.vue` 中通过 `import { ... } from './components'` 一次性引入。

#### （二）布局的动态类名

```js
const classObj = computed(() => ({
  hideSidebar: !sidebar.value.opened,     // 侧边栏收起
  openSidebar: sidebar.value.opened,      // 侧边栏展开
  withoutAnimation: sidebar.value.withoutAnimation,   // 切换时是否禁用动画
  mobile: device.value === 'mobile'       // 是否为移动端
}))
```

根节点 `app-wrapper` 绑定这些类名，配合 `layout` 的 SCSS 样式控制侧边栏宽度、过渡动画与移动端抽屉行为。这是"**状态驱动样式**"的典型做法：组件本身不直接操作 DOM 宽度，而是通过切换类名让 CSS 完成变化。

#### （三）响应式：设备类型的判断

```js
const { width, height } = useWindowSize()    // @vueuse/core：窗口尺寸的响应式引用
const WIDTH = 992                            // 参考 Bootstrap 的断点

watchEffect(() => {
  if (width.value - 1 < WIDTH) {
    useAppStore().toggleDevice('mobile')
    useAppStore().closeSideBar({ withoutAnimation: true })
  } else {
    useAppStore().toggleDevice('desktop')
  }
})
```

- 窗口宽度小于 992 像素时，设备类型切换为 `mobile`，并自动收起侧边栏；
- 移动端侧边栏展开时，显示 `drawer-bg` 遮罩，点击遮罩调用 `closeSideBar`，关闭抽屉。

> 注意：`watchEffect` 会在 `width` 变化时自动执行，不需要手动监听 resize 事件。这是 `@vueuse/core` 带来的便利（第 7 课的响应式知识）。

#### （四）侧边栏：`Sidebar`

- `sidebarRouters` 来自 `permission` store（第 17 课生成的侧边栏数据）；
- `isCollapse = !appStore.sidebar.opened`，传给 `el-menu` 的 `:collapse`，控制菜单折叠；
- 每个菜单项由递归组件 `SidebarItem` 渲染，支持多级菜单；`Link` 处理外链，`Logo` 显示系统 Logo。

> 侧边栏的数据是**动态生成**的，因此不同角色登录后看到的菜单不同。这与第 17、18 课的内容一脉相承。

#### （五）导航栏：`Navbar` 与 `navType`

`Navbar` 中的核心分支：

```vue
<hamburger :is-active="appStore.sidebar.opened" @toggleClick="toggleSideBar" />
<breadcrumb v-if="settingsStore.navType == 1" />
<top-nav v-if="settingsStore.navType == 2" />
<template v-if="settingsStore.navType == 3"> ... </template>
```

| `navType` | 模式 | 特点 |
| --- | --- | --- |
| 1 | 纯左侧 | 侧边栏承载全部菜单，顶部显示面包屑 |
| 2 | 混合 | 顶部导航显示一级菜单，侧边栏显示当前一级菜单下的子菜单 |
| 3 | 纯顶部 | 菜单全部在顶部，侧边栏不显示菜单 |

顶部导航 `TopNav` 使用的是 `topbarRouters`（第 17 课的 `setTopbarRoutes`）；侧边栏在混合模式下展示的是当前激活的一级菜单的子项。

> 实验建议：在设置面板切换 `navType`，分别观察三种模式下侧边栏与顶部导航的变化。

#### （六）标签栏与主内容区

- `TagsView` 由 `layout/index.vue` 中的 `v-if="needTagsView"` 决定是否渲染（它受 `settingsStore.tagsView` 等设置影响，第 14 课讲过标签数据）；
- `AppMain` 负责 `router-view` 与 `keep-alive`，其 `include` 来自 `tagsViewStore.cachedViews`（第 9 课讲过缓存）；
- 两者组合使页面切换既有标签，又能保留组件状态。

#### （七）`Hamburger` 与 `Breadcrumb`

- `Hamburger`：顶部的折叠按钮，`is-active` 表示当前展开状态，点击后触发 `toggleClick`，`Navbar` 再调用 `appStore.toggleSideBar`；
- `Breadcrumb`：根据当前路由的匹配链生成面包屑，路由的 `meta.breadcrumb: false` 会让其不显示（第 15 课）。

### 25.3 知识讲解

#### （一）`src/settings.js`：默认配置

```js
export default {
  title: import.meta.env.VITE_APP_TITLE,  // 网页标题（来自环境变量）
  sideTheme: 'theme-dark',                // 侧边栏主题：theme-dark / theme-light
  showSettings: true,                     // 是否显示设置面板
  navType: 1,                             // 导航模式：1 纯左侧 / 2 混合 / 3 纯顶部
  tagsView: true,                         // 是否显示标签栏
  tagsViewPersist: false,                 // 标签页是否持久化
  tagsIcon: false,                        // 标签是否显示图标
  tagsViewStyle: 'card',                  // 标签样式：card 卡片 / chrome 谷歌风格
  // ... fixedHeader、sidebarLogo、dynamicTitle、footerVisible、footerContent 等
}
```

这些是**出厂默认值**。用户在设置面板中的修改会覆盖它们。

#### （二）默认值与用户设置的合并

第 13 课讲过 `settings` store 的初始化规则，这里再回顾关键一点：

```js
const storageSetting = JSON.parse(localStorage.getItem('layout-setting')) || ''
navType: storageSetting.navType === undefined ? navType : storageSetting.navType
```

- 用户保存过的设置（`localStorage` 中的 `layout-setting`）优先；
- 没有保存过则使用 `settings.js` 的默认值；
- 判断使用 `=== undefined`，保证 `false`、`0` 等合法值不被误判（第 13 课已强调）。

#### （三）设置面板：`Settings` 组件

`src/layout/components/Settings/index.vue` 负责：

1. 提供各设置项的表单控件（开关、单选、颜色选择器等）；
2. 修改时调用 `settingsStore.changeSetting({ key, value })`，更新 store 状态；
3. 面板底部的"保存配置"按钮（`saveSetting`）把选中的字段写入 `localStorage` 的 `layout-setting`；
4. "恢复默认"（`resetSetting`）会删除 `tags-view-visited` 与 `layout-setting`，显示加载遮罩，约 1 秒后刷新页面。

`settings` store 还提供 `changeSetting` 通用方法，实现很简洁，只允许修改 state 中已经存在的键：

```js
changeSetting(data) {
  const { key, value } = data
  if (this.hasOwnProperty(key)) {
    this[key] = value
  }
}
```

> 设计思考：`hasOwnProperty` 检查是一道简单的"白名单"，避免设置面板误写入不存在的字段。

#### （四）主题色与颜色派生：`utils/theme.js`

`settings` store 的默认主题色为 `#409EFF`。主题色需要派生出一系列相关颜色（浅色背景、深色等）。`utils/theme.js` 导出了这些函数：

| 函数 | 作用 |
| --- | --- |
| `hexToRgb` / `rgbToHex` | 颜色格式互转 |
| `mixHexColors(fg, bg, t)` | 按比例混合两种颜色 |
| `getLightColor(color, level)` | 基于主色生成更浅的颜色 |
| `getDarkColor(color, level)` | 基于主色生成更深的颜色 |
| `softenPrimaryForDark(theme)` | 暗色模式下柔化主色，避免刺眼 |
| `handleThemeStyle(theme)` | 派生颜色并应用到页面（入口） |

`settings` store 的 `toggleTheme` 切换暗黑模式后，会在 `nextTick` 中调用 `handleThemeStyle(this.theme)` 重新应用主题。

```js
// src/layout/index.vue 根节点 app-wrapper 的内联样式（节选）
:style="{ '--current-color': theme, '--current-color-light': theme + '1a', ... }"
```

这里的 `theme + '1a'`（十六进制的 `1a` 即约 10% 透明度）是一个小技巧：直接拼接 8 位 HEX 颜色，实现带透明度的浅色背景。

> **原理**：样式表中引用 `var(--current-color)` 的地方会随变量变化而自动更新，因此换主题色时无需重新渲染组件。

#### （五）暗黑模式的两层实现

暗黑模式在第 11 课讲过 Element Plus 的部分，这里补充项目的完整链路：

1. `settings` store 通过 `useDark()` 切换 `<html>` 的 `dark` 类（`toggleTheme` 中的 `toggleDark`）；
2. Element Plus 的暗色 CSS 变量随之生效（组件变色）；
3. 项目自己的 `theme.js` 再根据暗色模式调整主色（`softenPrimaryForDark`）。

两层分工：**组件库负责通用颜色，项目负责品牌主色**。

#### （六）样式目录：`src/assets/styles`

| 文件 | 作用 |
| --- | --- |
| `index.scss` | 全局样式入口，被 `main.js` 引入 |
| `variables.module.scss` | SCSS 变量（颜色、尺寸），可在 `.vue` 中以模块方式引用 |
| `mixin.scss` | SCSS 混入（mixin），复用的样式片段 |
| `ruoyi.scss` | 框架通用样式（如 `mb8` 等间距工具类） |
| `sidebar.scss` | 侧边栏相关样式 |
| `btn.scss` | 按钮样式补充 |
| `element-ui.scss` | 对 Element Plus 组件的样式覆盖 |
| `transition.scss` | 过渡动画，如 `fade-transform` 相关样式 |

> 阅读提示：`mb8`（间距工具类）在用户页中大量出现，它就定义在 `ruoyi.scss` 中，这是"工具类优先"的写法。

#### （七）`variables.module.scss` 与 JS 互通

`settings` 或其它组件有时需要读取 SCSS 变量（如侧边栏宽度）。`variables.module.scss` 可以通过 `:export` 把变量导出到 JS 中使用。这种"样式与逻辑同步"的做法，可以避免在两处写死同一个值。

### 26.3 知识讲解

#### （一）`Pagination`：分页组件

在用户页中的用法：

```vue
<pagination v-show="total > 0" :total="total"
  v-model:page="queryParams.pageNum"
  v-model:limit="queryParams.pageSize"
  @pagination="getList" />
```

组件的关键设计（回顾第 8 课）：

| 项目 | 说明 |
| --- | --- |
| `total` | 必填，数据总数 |
| `page` / `limit` | 当前页与每页条数，通过 `v-model:page`、`v-model:limit` 双向绑定 |
| `pageSizes` | 可选的每页条数，默认 `[10, 20, 30, 50]` |
| `layout` | 分页栏布局，默认 `'total, sizes, prev, pager, next, jumper'` |
| `autoScroll` | 翻页后是否滚动到顶部（默认 `true`） |
| `hidden` | 是否隐藏 |
| `@pagination` | 页码或条数变化时触发，参数为 `{ page, limit }` |

**两种事件的分工**：`update:page` / `update:limit` 负责**同步数据**（让 `queryParams` 更新），`pagination` 负责**触发查询**（调用 `getList`）。这种拆分让组件既能被 `v-model` 使用，又能通过事件通知业务。

> 注意：页面中 `v-show="total > 0"` 用于数据为空时隐藏分页。这比 `v-if` 保留了组件实例，但对于分页来说两者都可以。

### 27.3 知识讲解

#### （一）`DictTag`：字典标签

```vue
<dict-tag :options="sys_normal_disable" :value="scope.row.status" />
```

| 属性 | 类型 | 作用 |
| --- | --- | --- |
| `options` | 数组 | 字典数据，格式为 `{ label, value, elTagType, elTagClass }` |
| `value` | 任意 | 当前值，可以是单个值、数组或以分隔符连接的字符串 |
| `separator` | 字符串 | 多值分隔符，默认为逗号 |

内部逻辑（回顾第 8 课）：

1. 用 `computed` 把 `value` 统一转为数组：
   - `null`、`undefined`、`''` → `[]`；
   - 数字或布尔 → `[value]`；
   - 数组 → 每项转为字符串；
   - 字符串 → 按分隔符拆分。
2. 遍历数组，在 `options` 中找到对应项，渲染为 `el-tag`，并应用 `elTagType`（颜色）与 `elTagClass`（自定义样式）。

> 设计要点：`DictTag` 只负责**展示**，字典数据从哪里来由调用方决定（通常是 `useDict`，第 29 课）。这种分离让它可以在任何页面复用。

#### （二）`Editor`：富文本编辑器

```vue
<editor v-model="form.noticeContent" :min-height="192" />
```

| 属性 | 作用 |
| --- | --- |
| `v-model` / `modelValue` | 富文本的 HTML 内容 |
| `height` / `minHeight` | 编辑区高度 |
| `readOnly` | 只读模式 |
| `type` | `'url'` 时，图片上传使用 URL 方式（需要配置） |
| `fileSize` | 上传文件的大小限制（MB） |

实现要点：

- 底层基于 `@vueup/vue-quill`（`package.json` 中为 1.2.0），并通过 `overrides` 把 `quill` 锁定为 `2.0.2`（第 0 课提过）；
- **向外同步**：编辑内容变化时，通过 `emit('update:modelValue', content)` 通知父组件（第 8 课讲过的 `v-model` 约定）；
- **向内同步**：通过 `watch(() => props.modelValue, ...)` 监听外部值的变化，并写回编辑器（例如打开编辑弹窗时回填内容）。

> **注意**：富文本内容是 HTML 字符串。展示时如果直接渲染用户输入的 HTML，就可能带来 **XSS 风险**（第 39 课会详细讨论）。

#### （三）`IconSelect`：图标选择器

```vue
<icon-select ref="iconSelectRef" @selected="selected" :active-icon="form.icon" />
```

- 内部通过 `requireIcons.js` 使用 `import.meta.glob` 收集 `src/assets/icons/svg/*.svg` 中的图标名，以网格形式展示，顶部搜索框按名称过滤；
- `activeIcon` 用于高亮当前选中项（`active` 类）；
- 组件**没有 `v-model`**：点击图标后触发 `selected` 事件，参数为图标名（字符串），父组件的 `selected` 函数负责把它写入表单（如 `form.icon = name`）；菜单管理页的 `form.icon` 最终被保存；
- 点击后组件会关闭自身弹出层（`selectedIcon` 中调用了 `document.body.click()`）。

> 与第 5 课的 SVG 插件呼应：图标文件位于 `src/assets/icons/svg`，由 SVG 插件统一注册为 SVG 符号。

定时任务的 `cron` 表达式通常很难手写，因此项目提供了可视化的 `Crontab` 组件：

```vue
<el-input v-model="form.cronExpression" placeholder="请输入cron执行表达式">
  <template #append>
    <el-button @click="openCron = true">生成表达式</el-button>

```

- 组件包含 `second`、`min`、`hour`、`day`、`month`、`week`、`year` 等子组件，分别处理对应时间段的选择；
- `expression` 是传入的初始表达式，用于回显；
- 用户确认后，组件通过 `fill` 事件把生成的表达式交给父组件（如 `crontabFill` 函数），由父组件写入表单；
- `hide` 事件用于关闭弹窗。

> 常见误区：`Crontab` 生成的表达式是**前端的表达式**，后端的调度框架是否支持所有写法（如"周"与"日"的互斥写法），需要以后端为准。

#### （一）`parseTime`：日期格式化

```js
export function parseTime(time, pattern) {
  // 支持：Date 对象、时间戳、日期字符串
  // pattern 例如 '{y}-{m}-{d} {h}:{i}:{s}'
}
```

- 页面中常用于表格的时间列：`parseTime(scope.row.createTime)`；
- `pattern` 参数控制输出格式，占位符包括 `{y}`（年）、`{m}`（月）、`{d}`（日）、`{h}`（时）、`{i}`（分）、`{s}`（秒）等；
- 不传 `pattern` 时使用默认格式（一般为 `{y}-{m}-{d} {h}:{i}:{s}`）。

> 阅读建议：在 `parseTime` 中找出它如何处理"空值返回 `null`"、"纯数字字符串视为时间戳"、"字符串中的 `-` 替换为 `/`"这三种情况。

#### （二）`addDateRange`：日期区间参数

用户页的查询代码：

```js
listUser(proxy.addDateRange(queryParams.value, dateRange.value))
```

`addDateRange` 的作用是把日期选择器的区间（`dateRange = ['2024-01-01', '2024-01-31']`）转换为查询参数中的 `params` 对象：

```js
// 调用后 queryParams 变为：
{ pageNum: 1, pageSize: 10, params: { beginTime: '2024-01-01', endTime: '2024-01-31' } }
```

- 第三个参数 `propName` 可以指定字段名：传 `'Create'` 会生成 `beginCreate`、`endCreate`（未传时为 `beginTime`、`endTime`）；
- 结合第 21 课的 `tansParams`，最终会被序列化为 `params[beginTime]=...&params[endTime]=...`。

这就是"页面的日期区间 → 后端能识别的查询参数"的完整转换链路。

#### （三）`handleTree`：扁平数据转树

后端常以扁平列表返回部门、菜单数据，每条记录包含 `id` 与 `parentId`。`handleTree` 把它转为树形结构：

```js
const tree = handleTree(deptList, 'deptId', 'parentId')
// 结果：[{ deptId: 1, children: [{ deptId: 2, ... }] }, ...]
```

参数说明：

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `data` | — | 扁平数组 |
| `id` | `'id'` | 主键字段名 |
| `parentId` | `'parentId'` | 父键字段名 |
| `children` | `'children'` | 生成的子节点字段名 |

处理思路（简化理解）：

1. 先遍历一遍，建立 `id → 节点` 的映射，并为每个节点补上空的 `children` 数组；
2. 再遍历一遍，把每个节点挂到父节点的 `children` 中；
3. 在数据中找不到父节点的节点（包括 `parentId` 指向不存在的记录）作为根节点返回。

> 在用户页中，`handleTree` 用于把部门列表转为 `deptOptions`，供左侧树和部门选择器使用。

#### （四）`selectDictLabel` 与 `selectDictLabels`

```js
selectDictLabel(datas, value)               // 返回单个标签
selectDictLabels(datas, value, separator)   // 返回多个标签拼接的字符串
```

- `datas` 是字典数组（`{ label, value }`），`value` 是字典值；
- `selectDictLabel` 在 `value` 为 `undefined` 时返回空字符串，找不到匹配项时返回原值；
- 与 `DictTag` 的区别：`selectDictLabel` 返回**文本**，适合在脚本中拼接字符串（如导出的 Excel 或提示信息），`DictTag` 返回**组件**，适合页面展示。

#### （五）`resetForm`：重置表单

```js
export function resetForm(refName) {
  // 通过 ref 名找到表单实例并调用 resetFields()
}
```

用法：`proxy.resetForm("queryRef")`，其中 `queryRef` 是模板中 `el-form` 的 `ref` 名称（第 11 课）。它封装了"找到表单 → 重置校验与数据"这两步。

#### （六）`parseStrEmpty`：空值安全的字符串

它把假值（空字符串）以及字符串形式的 `"undefined"`、`"null"` 统一转为空字符串 `""`，其它值原样返回，用于避免把无意义的文字显示或拼入参数中。

#### （七）`mergeRecursive`：递归合并对象

```js
export function mergeRecursive(source, target) {
  // 递归合并两个对象：target 中的属性覆盖 source 中同名属性，嵌套对象逐层合并
}
```

它常用于"默认配置 + 自定义配置"的合并场景。与普通的 `Object.assign` 相比，它会深入嵌套对象，而不是整体替换。

#### （八）`sprintf`：格式化字符串

```js
export function sprintf(str) {
  // 把字符串中的 %s 依次替换为其后的参数；参数不足时返回空字符串
}
```

### 29.3 知识讲解

#### （一）`useDict`：字典的获取

```js
const { sys_normal_disable, sys_user_sex } = useDict('sys_normal_disable', 'sys_user_sex')
```

- 支持一次传入多个字典类型，返回对象，可解构为响应式的字典数组；
- 内部流程（第 13 课讲过）：先查 `dict` store 缓存，未命中则调用 `getDicts` 接口，把结果转换为 `{ label, value, elTagType, elTagClass }` 格式并写入缓存；

> 注意：`useDict` 返回的是 `ref` 形式的数据，由于是异步加载，初次渲染时数组可能为空，之后会自动更新。这是响应式数据的正常表现。

`useDict` 通过 `vite/plugins/auto-import.js` 配置为自动导入（第 5 课讲过 Vite 插件），所以页面中可以直接使用而无需 `import`。

#### （二）`validate.js`：常用校验函数

| 函数 | 校验内容 |
| --- | --- |
| `isEmpty(value)` | 是否为空（`null`、`undefined`、`''`、字符串 `"undefined"`） |
| `isExternal(path)` | 是否为外部链接 |
| `isHttp(url)` | 是否为 http/https 地址 |
| `validUsername(str)` | 判断是否为模板示例用户（仅 `admin`、`editor`），**不是**用户名格式校验 |

| `isString` / `isArray` | 类型判断 |
| `isPathMatch(pattern, path)` | 路径模式匹配（第 16 课） |

这些函数既可以在 `el-form` 的自定义校验器中使用，也可以在普通逻辑中判断。

示例（自定义校验器，这里用正则演示，而不是 `validUsername`）：

```js
const validateCode = (rule, value, callback) => {
  if (!/^[a-zA-Z][a-zA-Z0-9_]{2,19}$/.test(value)) {

  }

```

#### （三）`passwordRule.js`：密码复杂度规则

这个文件体现了"**根据后台配置动态生成校验规则**"的思路。文件开头的注释说明了 `chrtype` 的含义：

| chrtype | 规则 |
| --- | --- |
| `0`（默认） | 任意字符，但不能包含 `< > " ' \ \|` |
| `1` | 纯数字（0–9） |
| `2` | 纯英文字母（a–z、A–Z） |
| `3` | 字母与数字，且必须同时包含 |
| `4` | 字母、数字与特殊字符（`~!@#$%^&*()-=_+`），且必须同时包含 |

```js
const pwdChrType = ref(cache.session.get('pwrChrtype') || '0')   // 读取后台配置的密码类型
const PWD_RULES = { '0': { pattern, message }, '1': { ... }, /* ... */ '4': { ... } }

export function usePasswordRule() {
  const pwdValidator = computed(() => { /* 根据 pwdChrType 选择规则 */ })
  const pwdPromptValidator = computed(() => { /* 生成提示文字 */ })
  return { pwdValidator, pwdPromptValidator }
}
```

要点：

1. **配置来源**：`pwrChrtype` 在获取用户信息（`user.js` 中的 `getInfo`）时写入 `sessionStorage`（第 13 课）。这就是"后台决定密码规则，前端据此校验"的链路；
2. **规则生成**：`usePasswordRule` 返回的是 `computed`，类型变化时规则自动更新；
3. **使用方式**：在用户页的表单中，`pwdValidator` 作为密码 `form-item` 的 `:rules`（第 11 课讲过）；
4. **前后端一致**：前端校验是为了体验，后端仍需用同样的规则再次校验。

#### （四）`jsencrypt.js`：RSA 加密工具

```js
import JSEncrypt from 'jsencrypt/bin/jsencrypt.min'

const publicKey = 'MFwwDQYJKoZIhvcNAQEB...'     // 公钥
const privateKey = 'MIIBVAIBADANBgkqhkiG9w0...'  // 私钥

export function encrypt(txt) { /* 用公钥加密 */ }
export function decrypt(txt) { /* 用私钥解密 */ }
```

在本项目中的实际用途：`login.vue` 中，勾选"记住密码"时，把密码加密后写入 Cookie：

```js
Cookies.set("password", encrypt(loginForm.value.password), { expires: 30 })
```

登录页初始化时，若 Cookie 中存在 `password`，则通过 `decrypt` 还原并回填到表单（`login.vue` 中 `password === undefined ? ... : decrypt(password)`）。

#### （五）安全边界：必须认真对待的问题

这是本课最重要的部分。请仔细阅读：

| 观察 | 风险 |
| --- | --- |
| **私钥写在前端代码中** | 任何人查看页面的 JS 文件，都能拿到私钥。因此这里的"加密"只能起到**混淆**作用，不能提供真正的保密性。 |
| **公钥与私钥成对出现在同一文件** | 加解密都在前端完成，等同于把"锁"和"钥匙"放在一起。 |
| **记住密码的 Cookie 可被读取** | 即使加密，Cookie 内容一旦被窃取，攻击者仍可能利用同样的前端代码解密。 |
| **登录请求中的密码未做前端加密** | 登录请求直接提交表单中的 `password`，并未经过 `encrypt`（`encrypt` 只用于"记住密码"的 Cookie）。因此它依赖 HTTPS 保证传输安全。 |

**正确的做法**：

1. **私钥只应存在服务端**，前端只持有公钥（如果确实需要前端加密）；
2. **密码传输应使用 HTTPS**，并由后端做哈希存储；
3. **"记住密码"功能本身风险较高**，更安全的做法是使用"记住登录状态"（如长期有效的 Token，且可撤销），而不是保存密码；
4. 前端加密不能替代后端安全，也不能替代 HTTPS。

> 这个问题在第 39 课"安全"一节会再次讨论。学习的重点是：**能识别出"前端代码中不应该存在的秘密"**。

#### （六）综合：一个表单的校验链路

以"新增用户"为例：

```
用户输入 → el-form-item 的 rules（userName、phonenumber 等，来自 rules 对象）
         → 密码字段的 :rules="pwdValidator"（来自后台 pwrChrtype 配置）
         → 点击确定 → validate()
         → 通过 → addUser(form) → 后端再次校验（最终防线）
```

### 30.3 知识讲解

#### （一）`$modal` 的方法族

`src/plugins/modal.js` 按"消息形态"分为四类，每类又有统一的语义变体：

| 类别 | 方法 | 形态 | 典型场景 |
| --- | --- | --- | --- |
| 消息（Message） | `msg`、`msgError`、`msgSuccess`、`msgWarning` | 顶部短暂提示，自动消失 | 操作成功、表单错误 |
| 通知（Notify） | `notify`、`notifyError`、`notifySuccess`、`notifyWarning` | 右上角通知，可包含标题与较长内容 | 错误详情、系统提醒 |
| 弹框（Alert） | `alert`、`alertError`、`alertSuccess`、`alertWarning` | 模态提示框，需要用户确认 | 重要提示 |
| 交互框 | `confirm`、`prompt` | 带确认/取消按钮，返回 Promise | 删除确认、输入内容 |
| 加载 | `loading`、`closeLoading` | 全屏遮罩加载 | 长时间操作 |

#### （二）典型用法

```js
// 成功提示
proxy.$modal.msgSuccess("修改成功")

// 删除确认（返回 Promise）
proxy.$modal.confirm('是否确认删除用户编号为"' + userIds + '"的数据项？').then(function () {
  return delUser(userIds)
}).then(() => {
  getList()
  proxy.$modal.msgSuccess("删除成功")
}).catch(() => {})     // 用户点击取消时，Promise 会 reject，需要捕获避免控制台报错

// 加载遮罩
proxy.$modal.loading("正在导出数据，请稍候...")
// ... 操作完成后
proxy.$modal.closeLoading()
```

用户页中的删除流程，正是"确认 → 请求 → 成功提示 → 刷新列表"的完整链路。

> 注意：`confirm` 的 Promise 在用户点击取消时会 **reject**。如果不写 `.catch`，浏览器控制台会出现未捕获的错误，因此几乎所有 `confirm` 后面都跟着 `.catch(() => {})`。

#### （三）为什么要统一封装

直接调用 `ElMessage`、`ElMessageBox` 也能实现功能，但统一封装有以下好处：

1. **风格统一**：所有提示的时长、位置、标题文字由一处决定；
2. **调用简洁**：`msgSuccess("...")` 比 `ElMessage({ message: "...", type: "success", duration: 3000, ... })` 简短；
3. **便于替换**：如果将来更换 UI 库，只需修改 `modal.js`，业务代码无需改动；
4. **便于统一处理**：例如给所有确认框加入默认文案、按钮样式等。

#### （四）`request.js` 的错误提示与页面提示的分工

| 位置 | 负责的提示 | 举例 |
| --- | --- | --- |
| `request.js` 拦截器 | 网络错误、HTTP 异常、统一错误码（500、601、其它） | "后端接口连接异常"、"系统接口超时" |
| 页面业务代码 | 业务成功提示、操作确认 | "修改成功"、"是否确认删除" |

**原则**：
- 通用的、与业务无关的错误，交给拦截器统一提示，页面不需要重复处理；
- 与业务相关的成功反馈、确认操作，由页面通过 `$modal` 明确表达。

这样页面代码既不会重复写错误处理，也能保留必要的交互反馈。

#### （五）`loading` 的使用注意

- `loading` 会显示全屏遮罩，**必须确保在所有分支都调用 `closeLoading`**，包括错误分支，否则遮罩会一直存在；
- 如果是局部加载（如表格加载），应使用组件自身的 `v-loading` 指令（用户页的 `loading` 变量即属于这种方式），而不是全屏遮罩。

5. 风格统一、调用简洁、便于替换底层 UI 库、便于统一加入默认行为。

</details>

## 本章小结

| 课时 | 核心问题 | 关键结论 |
| --- | --- | --- |
| 第 24 课 | 页面由哪些部分组成？ | 侧边栏、导航栏、标签栏、主内容区；`navType` 决定菜单位置；窗口宽度决定设备模式 |

**本章的一个核心观念**：通用组件与工具函数的价值在于**把重复的模式沉淀为可复用的约定**。学习时既要会用它们，也要分辨哪些约定是"便利"（如自动导入），哪些是"必须保持的安全边界"（如不把私钥放进前端、后端必须二次校验）。
