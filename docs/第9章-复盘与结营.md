### 41.3 知识讲解

#### （一）一次请求的完整旅程

以"打开用户管理页面"为例，把整个过程串起来：

```
① 浏览器加载 index.html
   └─ <script type="module" src="/src/main.js">（第 3 课）

② main.js 创建应用
   ├─ createApp(App)，注册 Element Plus、Pinia、Router（第 10–13 课）
   ├─ 注册全局组件、指令、插件（第 10 课）
   └─ import './permission'，挂载路由守卫（第 16 课）

③ 路由守卫 router.beforeEach（src/permission.js）
   ├─ 有 Token（getToken 来自 Cookie）？否 → 跳转 /login（白名单除外）
   ├─ 首次进入且无用户信息 → useUserStore().getInfo()（第 13 课）
   ├─ usePermissionStore().generateRoutes() → 根据菜单生成路由（第 17 课）
   └─ router.addRoute(...) 把动态路由加入路由表

④ 路由匹配到 /system/user
   └─ 组件由 permission.js 的 loadView 按路径懒加载 views/system/user/index.vue（第 17、39 课）

⑤ 页面 setup 执行
   ├─ useDict 获取字典（第 29 课）
   ├─ getConfigKey 读取参数（第 34 课）
   └─ getList() → listUser(queryParams)（第 31 课）

⑥ 接口模块 src/api/system/user.js
   └─ 调用 request({ url, method, params })（第 20、22 课）

⑦ 请求拦截器 src/utils/request.js
   ├─ 携带 Authorization: Bearer <token>（第 21 课）
   ├─ GET 参数序列化为查询串（tansParams，第 21 课）
   └─ POST/PUT 重复提交检测（第 21、39 课）

⑧ 后端处理，返回 { code, msg, data / rows, total }

⑨ 响应拦截器
   ├─ code 200 → 返回数据
   ├─ code 401 → 提示会话过期并跳转登录（第 21 课）
   └─ 500 / 601 / 其它 → 统一错误提示（第 22 课）

⑩ 页面渲染
   ├─ userList、total 更新（响应式，第 7 课）
   ├─ el-table、Pagination、DictTag 重新渲染（第 26、27 课）
   └─ 用户点击操作 → $modal 确认与提示（第 30 课）
```

> 这条链路可以概括为：**入口 → 守卫 → 动态路由 → 页面 → 接口 → 拦截器 → 响应渲染**。每一层只负责自己的事情，这正是前面七章不断强调的分层思想。

#### （三）版本对比：RuoYi-Vue2、Vue3、Vue3-TypeScript

根据仓库 `README.md` 中的"版本对比"表格（节选）：

| 维度 | RuoYi-Vue2 | RuoYi-Vue3 | RuoYi-Vue3-TypeScript |
| --- | --- | --- | --- |
| 前端框架 | Vue 2 | Vue 3 | Vue 3 |
| 脚本语言 | JavaScript | JavaScript | TypeScript |
| 构建工具 | Vue CLI | Vite | Vite |
| UI 组件库 | Element UI | Element Plus | Element Plus |
| 状态管理 | Vuex | Pinia | Pinia |
| 路由管理 | Vue Router 3 | Vue Router 4 | Vue Router 4 |
| 核心特点 | 技术栈经典稳定，社区资料丰富，当前维护重心已转移 | 现代技术栈，开发体验与性能更优，官方主推的活跃版本 | 类型加持，减少沟通成本（以 README 原文为准） |

本课程基于 **RuoYi-Vue3**（JavaScript 版本）。

#### （四）迁移成本与收益

从 Vue2 迁移到 Vue3 的版本，可以从以下角度讨论：

| 角度 | 收益 | 成本 / 风险 |
| --- | --- | --- |
| 框架生态 | Vue 3 是当前主推版本，社区与第三方库持续更新 | Vue 2 的部分第三方库可能没有 Vue 3 版本 |
| 语法 | 组合式 API 便于按功能组织逻辑（第 7 课） | 团队需要学习新的写法，并能区分两种风格 |
| 状态管理 | Pinia 结构简单，支持 TypeScript（第 12 课） | Vuex 的存量代码需要重写 |
| 路由 | Vue Router 4 的 API 有变化（第 15 课） | 路由守卫、动态路由的写法需要调整 |
| 构建 | Vite 启动快、热更新快（第 1 课） | 旧的 Vue CLI 配置需要迁移 |
| UI | Element Plus 的组件与 API 与 Element UI 接近，但不完全相同（第 11 课） | 需要逐个检查组件属性与事件的变化 |

> 结论：**迁移的收益主要在长期维护与开发体验，成本主要在一次性的改造与团队学习**。对于新项目，直接选择 Vue3 版本通常更合适；对于存量 Vue2 项目，应根据业务规模、团队能力与维护周期评估。

Vue3-TypeScript 版本则是在 Vue3 基础上增加类型约束，适合中大型团队与需要长期维护的项目，代价是初期的类型编写成本。

<details>
<summary>参考答案（示例结构）</summary>

> 本项目的启动从 `index.html` 加载 `main.js` 开始，在这里注册 Element Plus、Pinia、Router 与各类全局组件。权限由路由守卫统一把关：未登录跳转登录页，登录后获取用户信息并根据菜单动态生成路由，页面按路径懒加载。接口统一封装在 `src/api` 中，所有请求经过 `request.js` 的拦截器：请求阶段携带 Token、序列化参数、防重复提交；响应阶段按错误码统一提示或跳转登录。状态方面，`src/store/modules` 下的 `app`、`user`、`permission`、`dict`、`settings`、`tagsView`、`lock` 等 store 各自负责一块全局数据，页面通过 store 与 api 协作。
>
> 我认为最值得学习的是"分层"：页面只关心数据与交互，接口与拦截器处理网络细节，权限与路由在入口统一控制。最需要注意的是"前端权限只是体验层"：按钮隐藏和路由守卫都可以被绕过，所有权限与数据校验必须在后端兜底，同时 Token 存放方式与 XSS 风险需要持续关注。

评分要点：能把四个方面串联起来，并给出具体的判断与依据，而不是只罗列文件名。

</details>

#### （二）综合自测题

1. 请说出 `permission.js` 中白名单的作用，并给出一个应当加入白名单的路径示例及理由。
2. `request.js` 的 `code === 401` 与 `code === 500` 分别代表什么？页面应如何感知它们？
3. 动态路由为什么需要 `router.addRoute`，而不是直接写进路由表？
4. 字典数据在页面中通过哪些环节被使用？如果新增字典数据后页面没有变化，应优先检查什么？
5. 为什么说"隐藏按钮"不是安全措施？请给出一个具体的绕过方式与对应的后端防护思路。
6. 设计器中"一份配置，两种输出"指的是什么？
7. 本项目中有哪两处 `v-html` 渲染动态内容？各自的风险与改进方向是什么？

<details>
<summary>参考答案</summary>

1. 白名单中的路径（如 `/login`、`/register`）无需登录即可访问，否则会被守卫重定向到登录页。应加入白名单的示例是 `/register`：注册页面本身面向未登录用户，必须允许访问。
2. `401` 表示会话无效或已过期，拦截器会提示用户并跳转登录；`500` 表示服务端错误，拦截器弹出错误提示并以 `Error` 形式拒绝 Promise，页面可通过 `catch` 感知。
3. 动态路由依赖后端返回的菜单，只有登录后才能确定；`addRoute` 允许在运行时把这些路由加入路由表。若写死，就无法按角色控制可访问的页面。
4. 环节包括：后端字典数据 → `useDict` 请求并缓存（第 29 课）→ `DictTag` 或下拉框渲染。新增数据后页面无变化，优先检查是否刷新了字典缓存（字典类型页的"刷新缓存"）。
5. 因为隐藏按钮只改变前端渲染，攻击者可以直接调用接口，或修改前端代码。防护思路是后端对每个接口校验权限标识与数据范围，并对非法请求返回拒绝。
6. 同一份配置既可以在设计器内部渲染为预览（`render.js`），也可以通过 `html.js`、`js.js`、`css.js` 输出为代码（第 38 课）。
7. 第一处是 `DetailView.vue` 中的公告正文（`noticeContent`），风险是富文本中的恶意脚本；第二处是 `HeaderSearch` 中的 `highlightText`，风险是原文本未转义。改进方向：对不可信内容做转义或净化，优先避免 `v-html`，改用插值或组件化渲染（第 39 课）。

</details>
